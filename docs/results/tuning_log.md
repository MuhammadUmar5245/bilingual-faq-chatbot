# NLP tuning log (Phase 3)

This log records what was changed to reach the NF-02 target (≥ 85 % accuracy) and why.
All numbers below were produced by running the code; the final numbers are in
[`results.md`](results.md) and are regenerated by `python -m nlp.evaluate` (from `backend/`).

## Evaluation protocol
- 361 held-out test queries (`data/test_queries.csv`), written separately from the 210 seed
  questions; 32 are out-of-scope and must produce the fallback.
- To avoid tuning on the numbers being reported, the test set is split by `query_id`:
  **odd ids = tuning split** (181 queries, used to choose thresholds and to inspect errors),
  **even ids = held-out split** (180 queries, never inspected or used for any decision).
- Each method's threshold is chosen independently on the tuning split, so the comparison
  between keyword / TF-IDF / SBERT / hybrid is fair.

## Step 0 — first measurements (exploration, before any tuning)
Top-1 accuracy on in-scope queries, ignoring thresholds:
TF-IDF 80.2 % (EN 83.6 %, AR 73.1 %), SBERT 72.0 % (EN 74.7 %, AR 66.3 %).

**Finding 1 — the 0.75 TF-IDF threshold from Chapter 3.6 is rarely reached.** Correct TF-IDF
matches have a median cosine of about 0.50, so with 0.75 almost every query falls through
to SBERT, which on its own is weaker than TF-IDF. The spec hybrid (TF-IDF ≥ 0.75, else SBERT)
therefore behaves almost like SBERT alone.

## Step 1 — score fusion in the SBERT stage (kept)
When TF-IDF confidence is below 0.75, the SBERT stage now ranks FAQs by
`fused = w·TF-IDF + (1−w)·SBERT` instead of SBERT alone. SBERT is still only used as the
fallback stage, as specified in FR-03, but it no longer throws away the lexical evidence.
On the tuning split the fusion raised in-scope top-1 accuracy from ~72 % (SBERT) to ~86 %.
The weight w and the fused threshold are tuned on the tuning split (grid w ∈ {0.3…0.7},
threshold 0.05–0.95). The chosen values are **w = 0.6, fused threshold = 0.35**.

First full evaluation after Step 1 (`evaluate.py`): hybrid **82.2 % held-out / 84.5 % full**,
spec hybrid 76.7 % / 74.0 %, TF-IDF 79.4 % / 77.6 %, SBERT 76.1 % / 73.7 %,
keyword 61.1 % / 60.9 %. This was below the 85 % target, mainly because of Arabic queries.

## Step 2 — Arabic preprocessing fixes (kept)
Errors on the tuning split showed that colloquial synonyms (e.g. `بالجوال`, `الايميل`) were
missed because the synonym table was applied before prefix stripping. Changes:
- synonym lookup now also tries the prefix-stripped token;
- the light stemmer also strips a leading `ب` (preposition) on long words;
- the `ين` suffix rule was removed (it damaged words such as `تحسين`).
A/B on the tuning split (Arabic, TF-IDF only): no stemming 54.1 %, prefix+suffix
stemming without `ب` 56.8 %, final 59.5 %.

## Step 3 — Arabic keywords in the knowledge base (kept)
The `keywords` column only contained English keywords, so Arabic queries could only match
the single Arabic question per FAQ. 3–5 Arabic keywords/synonyms (MSA and common Gulf usage)
were added to every FAQ in the same `keywords` column (CSV format unchanged); the retriever
routes Arabic keywords to the Arabic document and English keywords to the English document.
This is the same enrichment college staff can do from the admin dashboard.

To limit leakage, any keyword phrase that was identical (after normalisation) to a test
query was automatically removed before saving (28 phrases removed).

**Threat to validity:** the keywords and the test queries were written by the same author,
so some vocabulary overlap is unavoidable. The held-out split was not inspected, but the
true accuracy on queries from real students may be lower; this should be re-measured with
real student queries collected from the conversation logs (FR-07).

Result after Step 3: hybrid **85.6 % held-out / 87.3 % full** (target met).

## Tried and rejected (no improvement on the tuning split)
| Change | Tuning-split accuracy |
|---|---|
| Baseline at that point (fusion, w = 0.6) | 86.7 % |
| Expanding abbreviations (GFP, HEAC, OJT…) in the SBERT query | 86.7 % (no change) |
| Adding FAQ answers as extra SBERT documents (weight 0.9) | 85.6 % |
| Adding FAQ answers as extra TF-IDF documents (weight 0.5–0.8) | lower than without |
| Category-agreement boost from the FR-02 classifier (β = 0.02 / 0.05 / 0.08) | 86.7 / 85.1 / 84.5 % |

## Final configuration (used by the API)
| Parameter | Value | Where |
|---|---|---|
| TF-IDF stage threshold | 0.75 (unchanged, editable in admin settings) | `settings.confidence_threshold` |
| SBERT-stage (fused) threshold | 0.35 | `settings.sbert_threshold` |
| Fusion weight w | 0.6 | `settings.fusion_weight` |
| TF-IDF features | stemmed word 1–2-grams (0.6) + char 3–5-grams (0.4) | `nlp/tfidf_retriever.py` |
| SBERT model | paraphrase-multilingual-MiniLM-L12-v2 | `SBERT_MODEL` env var |

Observation for the report: with the 0.75 TF-IDF threshold only a small share of queries is
answered directly by TF-IDF (see "Hybrid answers by stage" in `results.md`); panel A of
`threshold_sweep.png` shows that lowering the TF-IDF threshold does not change hybrid accuracy
much, because the fused SBERT stage already uses the TF-IDF evidence. The 0.75 default was
therefore kept as the high-precision "fast path".
